# Campfire — Section B handoff

This folder contains the complete React + Tailwind feature module. It does not create an app, Supabase client, authentication UI, database migration, or teammates' features. GitHub returned “This repository is empty” when its contents were inspected, so there is no repository authentication implementation to audit. The contracts below are assumptions approved for this draft, not a verified existing schema.

## Files and installation

Copy the four `.js` / `.jsx` files to `src/campfire/`. Keep your existing configured client in `src/supabaseClient.js`, exporting `supabase` as a named export. If your project uses a default export, adjust the imports in `campfireApi.js` and `PhonePresencePage.jsx`. React, React DOM, Supabase JS v2, and Vite/Tailwind are supplied by the main app; these files do not change their configuration.

- `PhonePresencePage.jsx`: authentication check, permission button, orientation listener, simulation override, throttled persistence, phone connection registration.
- `SharedScreen.jsx`: exports the default shared display and named `StartSessionButton`.
- `orientation.js`: tilt geometry, hysteresis, serialized leading/trailing write throttle with retry.
- `campfireApi.js`: session writes, current user lookup, presence upsert, Realtime subscription/snapshot reconciliation/cleanup.

## Assumed database contract — no migration is included

| Table | Required columns / behavior |
| --- | --- |
| `sessions` | `id` generated by the database; `room_id`; `is_active` boolean; nullable `ended_at` timestamp |
| `session_presence` | `session_id`; `user_id`; `state` text or enum accepting exactly `down` and `up` |

`session_presence` must already have a unique constraint on `(session_id, user_id)` for the upsert conflict target. Any other mandatory columns must have database defaults. `sessions.id` and the other IDs are assumed to be UUIDs. Presence IDs must refer to the authenticated user's ID and the relevant session. If the shared schema uses `status` instead of `state`, update the select, upsert, and row mapping in these files rather than adding a duplicate column.

The app's `public.sessions` study-session rows are unrelated to Supabase Auth's internal `auth.sessions` login sessions.

## Information for the authentication/backend owner

Provide a working signed-in Supabase client on both phone and shared-screen routes. The phone resolves its identity with `supabase.auth.getUser()`; it never accepts a user ID from a URL. Login, logout, account creation, and OAuth callbacks stay in your feature.

Your existing browser client must use a publishable key or legacy anon key, never a secret/service-role key. This module never reads, copies, logs, or stores passwords, access tokens, or refresh tokens. The Supabase client supplies authenticated requests and handles its configured session persistence/refresh. Its storage settings cannot be verified because no client code was supplied.

Required existing database policies:

- Session reads: room members only.
- Session creation and ending: the role your team chooses (for example, room host).
- Presence reads: authorized members of the session's room.
- Presence inserts and updates: `auth.uid() = user_id`, authorized room membership, and an active session. Enforce both INSERT checks and UPDATE policies/checks, because the client uses upsert.
- Ended sessions: reject further presence writes. A write already in flight when a session ends cannot be canceled reliably by the browser.

The `canEnd` prop only controls the button; database policies must enforce authorization. Start-button locking prevents repeated taps in one mounted button, but does not enforce one active session per room across clients. If the shared schema promises that rule, enforce it in the backend owner’s contract.

Enable Postgres Changes for `sessions` and `session_presence` in Supabase Realtime. Allow the authenticated clients to use the `campfire:<sessionId>` channel and Realtime Presence. This draft uses a normal public channel with no secret payload: only `user_id` is tracked. If the team requires private channels, configure the matching Realtime authorization policies and add `config: { private: true }` when constructing the channel.

## Information for the rooms/profile owner

Supply the complete participant roster for the session, not merely users with an existing presence row:

```js
const participants = [
  { user_id: 'authenticated-user-uuid', name: 'Avery', avatar_url: null },
];
```

Profiles and room-membership queries stay in your feature. Pass updated roster props if participants join or leave. Decide whether membership is fixed at session start or follows the room live. Until the roster is nonempty, the timer stays paused. Missing presence or an offline connection also pauses it. Use one phone page per user per session; multiple devices writing the same row have last-write-wins behavior.

## Information for the routing/integration owner

Suggested routes, implemented by the parent app:

- `/sessions/:sessionId/shared` → `<SharedScreen sessionId={sessionId} participants={participants} canEnd={isHost} />`

The room view mounts:

<StartSessionButton
  roomId={roomId}
  onStarted={sessionId => navigate(`/sessions/${sessionId}/shared`)}

Create a phone URL/QR code containing only the study-session ID. Each participant signs in on their own phone. Do not put credentials or tokens in share URLs. Configure the host to serve the Vite application for deep links, and serve over HTTPS for sensors on real devices. These are responsive web pages, not native apps.

## Request and state flow

1. The parent app signs users in through the existing Supabase client.
2. Start inserts `{ room_id, is_active: true }` and returns the generated study-session ID.
3. The phone checks its authenticated identity and loads the session after Realtime connects.
4. A tap calls the orientation permission API on browsers that require it. Other browsers attach the sensor listener without a permission-method call; missing APIs, denial, insecure contexts, and lack of sensor data show fallback guidance.
5. `cos(beta) * cos(gamma)` estimates the vertical screen normal. Enter `down` at `<= -0.8`; remain down until above `-0.65`. Null/invalid readings never qualify as down.
6. The simulation button forces `down`; disabling it restores the current sensor reading. A hidden phone page requests `up`, including when simulation is enabled. Browser suspension can prevent a final write, so Realtime connection presence is also checked.
7. The writer sends the most recent state at most once every two seconds, never overlaps requests, coalesces intermediate changes, and retries failed writes at the same rate. Unchanged successfully saved states cause no writes.
8. The shared screen subscribes before reading a snapshot, refreshes after database changes, and periodically reconciles. It pauses while disconnected, syncing, empty, ending, hidden, or any roster member is offline/not down.
9. Ending updates `ended_at` and `is_active: false`. Errors are displayed; success stops the timer. Subscription cleanup runs on unmount/session changes.

## Timing limits the team needs to know

The timer is a local display owned by one shared-screen tab. It resets on reload and is not guaranteed to match another shared-screen tab. No elapsed-time database field or authoritative timer service was supplied. Durable scoring, recovery, and exactly synchronized multiple displays require a separately agreed server-side timer contract.

Up/down changes have up to two seconds of throttle delay plus network/Realtime latency. The display intentionally pauses during snapshot reconciliation, so this is conservative demo timing rather than a precision scoring system. Phone disconnect recognition depends on Realtime's connection timeout; it is not instantaneous. A reconnect can briefly expose an old stored state until the phone's latest write arrives. Keep the phone page open and unlocked. Automatic screen-lock prevention is not included. Manual simulation is intentionally user-controlled and is not an anti-cheating mechanism.

The end timestamp uses the shared-screen client's clock because no server RPC/default for this action was provided.

## Verification and team acceptance

Local checks cover orientation boundaries and throttle behavior, and compile both JSX entry points. Live integration still requires your team's Supabase project, policies, and physical phones.

Before the demo, verify with two signed-in accounts:

1. A new session is inserted, the full roster appears, and missing phones keep the timer paused.
2. iOS allows/denies the explicit permission prompt correctly; desktop uses the simulation toggle.
3. Both phones down starts counting; lifting either pauses and flags that name; toggling simulation uses the same persistence path.
4. Rapid flips produce no more than one write every two seconds and eventually save the last state.
5. Disconnecting a phone eventually marks it offline and pauses the timer; disconnecting the shared screen pauses it.
6. Ending writes the expected columns and blocks subsequent presence updates through database policies.
7. A different room member cannot read this room; one user cannot write another user's presence; a non-host cannot end a host-only session.
